# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The Stellar Disbursement Platform (SDP) backend — a Go service that lets organizations disburse bulk payments to recipients over the Stellar network. "Users" are org staff using the SDP; "recipients"/"receivers" are the people getting paid. Single Go module (`github.com/stellar/stellar-disbursement-platform-backend`, Go 1.24), single binary (`stellar-disbursement-platform`) with subcommands for each service/role.

## Commands

```sh
go build -o $(GOPATH)/bin/stellar-disbursement-platform .   # or: make go-install
gotestsum --format-hide-empty-pkg --format pkgname-and-test-fails    # run tests (or: make go-test / go test ./...)
go test ./internal/data/... -run TestPaymentModel_GetByStellarTransactionID -v   # single test
golangci-lint run              # or: make go-lint
shadow ./...                   # shadow variable detection, or: make go-shadow
deadcode -test ./...           # or: make go-deadcode
exhaustive -default-signifies-exhaustive ./...   # or: make go-exhaustive
./gomod.sh                     # verify go.mod/go.sum, or: make go-mod
make go-check                  # runs all of the above (test, lint, shadow, mod, deadcode, exhaustive)
```

Most tests spin up a real ephemeral Postgres database per-package via `db/dbtest` (`dbtest.Postgres(t)`), **not mocks** — a running local Postgres (or the one from `dev/docker-compose.yml`) is required to run the suite. CI runs against `postgres:12-alpine` with `DATABASE_URL=postgres://postgres:postgres@localhost:5432/postgres?sslmode=disable`. CI also enforces an 84% coverage threshold and `goimports -local github.com/stellar/stellar-disbursement-platform-backend`.

Local full-stack dev environment (Docker Compose, multi-tenant DNS, HTTPS, demo wallet, Grafana/Prometheus) is documented in `dev/README.md`; `make setup` runs the interactive wizard (`tools/sdp-setup`) that generates `.env`.

## Architecture

### Three cooperating services, one binary

The CLI (`cmd/root.go` → `main.go`) exposes subcommands, the two important long-running ones being:

- **`serve`** (`cmd/serve.go`, `internal/serve/`) — Core service. Bundles the Admin API (port 8003, tenant provisioning), the Dashboard API (the main REST API consumed by the [SDP Dashboard frontend](https://github.com/stellar/stellar-disbursement-platform-frontend)), native SEP-10 (wallet auth) and SEP-24 (interactive deposit/registration) endpoint implementations, the wallet registration UI, and Prometheus metrics.
- **`tss`** (`cmd/transaction_submitter.go`, `internal/transactionsubmission/`) — Transaction Submission Service. Polls for queued payments and submits them to the Stellar network from a shared distribution account via rotating channel accounts, with fee-bump retries and Horizon error-class-based retry logic. See `internal/transactionsubmission/README.md` for the full flow diagram and channel-account CLI.

Core and TSS are **decoupled through the database only** — Core writes rows into `submitter_transactions`, TSS polls and updates them, Core reads back the result. There is no direct RPC between them today (planned to become a separate service/API later).

Other subcommands: `db` (migrations, see below), `message` (send a test SMS/email), `channel-accounts` (manage TSS channel accounts), `distribution-accounts`, `auth`, `tenants`, `integration-tests`.

### Multi-tenancy via Postgres schemas

One physical database, multiple schemas, routed by DSN `search_path` (see `db/router/router.go`):

- `admin` — tenant registry, provisioned once (`db admin migrate up`)
- `sdp_<tenant_name>` — one schema per tenant for Core/SDP tables (`db sdp migrate up --tenant-id=<id>` or `--all`)
- `tss` — shared by all tenants for transaction submission (`db tss migrate up`)
- `auth` tables also exist per install

Requests are resolved to a tenant by subdomain (dev setup adds `<tenant>.stellar.local` to `/etc/hosts`); `stellar-multitenant/pkg/tenant` and `internal/serve/middleware` carry tenant context through the request lifecycle. When touching DB code, check whether it needs to be tenant-scoped (`sdp_*`) vs. shared (`admin`/`tss`).

### Layout of the important packages

- `internal/data/` — all DB models (`*Model` structs, one per table/domain e.g. `PaymentModel`, `DisbursementModel`, `ReceiverWalletModel`), each holding a `dbConnectionPool db.DBConnectionPool`. `Models` (`internal/data/models.go`) is the aggregate root injected into handlers/services. Mirrors under `internal/data/mocks/` (mockery-generated, `testify/mock` — regenerate rather than hand-edit, header says `Code generated by mockery`).
- `internal/services/` — business logic/orchestration (disbursement management, payment-to/from-submitter, Circle integration, SEP-10, reconciliation, reports, invitations, etc.), consumed by `serve` handlers and by scheduled jobs.
- `internal/serve/httphandler/` — HTTP handlers (chi router, wired in `internal/serve/serve.go`); `internal/serve/middleware/`, `validators/`, `httpresponse/`, `httperror/` support them.
- `internal/scheduler/jobs/` — background jobs (`send_receiver_wallets_invitation_job`, `payment_to_submitter_job`, `payment_from_submitter_job`, `patch_anchor_platform_transactions_completion`, etc.), interval-configured via `SCHEDULER_*_JOB_SECONDS` env vars.
- `internal/transactionsubmission/` — TSS engine, channel account management, Horizon submission/monitoring.
- `internal/dependencyinjection/` — a small global keyed instance store (`SetInstance`/`GetInstance`/`CleanupInstanceBy{Key,Value}`) used to lazily construct and share singletons (DB pools, clients) across commands; instances implementing `io.Closer` are cleaned up automatically.
- `stellar-auth/` — standalone auth package (JWT, RBAC roles, API keys) used by Core; has its own `cmd/stellarauth` CLI.
- `stellar-multitenant/` — tenant provisioning service/CLI and `pkg/tenant` tenant-resolution logic.
- `db/migrations/` — SQL migrations split into `admin-migrations/`, `auth-migrations/`, `sdp-migrations/`, `tss-migrations/`, applied via `sql-migrate` (`db/migrations` + `cmd/db`). `db/dbtest/` builds ephemeral test databases from these.
- `internal/circle/`, `internal/bridge/` — external payment-rail integrations (Circle, Bridge).
- `internal/message/` — outbound SMS/email/WhatsApp abstraction (Twilio SMS/WhatsApp/SendGrid, AWS SES/SNS) behind a common dispatcher.
- `pkg/schema/` — shared distribution-account/schema types used across Core and TSS.

### State machines

Disbursements, payments, receiver wallets, and messages each follow an explicit state machine (see README.md's Mermaid diagrams for the exact transitions, e.g. Payment: `Draft → Ready → Pending → Success|Failed`, with `Failed → Pending` retries). Look for `*_state_machine.go` files beside the corresponding model/service before adding new transitions.

## Conventions

- Linting is strict and CI-enforced: `errcheck` (including blank-identifier assignments), `wrapcheck` (wrap errors on the way out — except `.Close()`, `.Rollback()`, `db.OpenDBConnectionPool`, `json.Marshal/Unmarshal`, etc., see `.golangci.yml`), `nilerr`/`nilnesserr`, `errorlint`, `unparam`, `unused`, full `staticcheck` (minus `QF1008`, `ST1000`). Mocks (`*.mock.go` paths) are excluded from linting.
- Imports must be `goimports`-grouped with local prefix `github.com/stellar/stellar-disbursement-platform-backend`, checked in CI against all non-mock `.go` files.
- PR titles: `feat|fix|refactor|ci|doc: short description`; PRs target `develop`, must stay focused, and refactor PRs should be kept separate from feature PRs (see `CONTRIBUTING.md`). Commit messages: imperative mood, present tense.
- New features/bug fixes need tests; refactors should add them where practical. Test files for a DB model typically spin up a real dbtest Postgres rather than mocking the DB layer — mocks (`internal/*/mocks`) are for mocking *other* internal collaborators/interfaces, not the database itself.
